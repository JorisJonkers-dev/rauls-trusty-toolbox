# Updating raul replaces it and its packages as one unit, and rolls back

`raul` can look for a newer release (ADR-0005) but cannot install one: the About and updates page links to the
release page. This ADR decides how `raul` installs a newer release itself (#179). One `raul` version carries one set of
Component versions (ADR-0016), so an update never moves one Component: it replaces `raul` and everything that ships
with it, together, or it changes nothing. Nothing in it runs until the person presses a button.

## The unit

The **install unit** is every file the release put on the machine for this install: the `raul` program, the
packaged nv-rs engine build under `components/nv-rs/` on Linux and Windows (macOS has none), `THIRD-PARTY-NOTICES.md`
and `LICENSE`. The linked Components (nvmod, loot-rs, lodwright-rs, ttwright-rs) are inside the `raul` file and need no
file of their own. The engine build is the only package that is a separate file, and it stays one until the play mode
(#260, nv-rs#353) links it; then the unit is `raul` plus notices and this ADR needs no change.

Each release adds `INSTALLED-FILES.sha256` to the unit: one `sha256sum` line for every other file in it. It is
generated by `release.yml` from the staged bundle, so it cannot disagree with what ships. The installed copy of it is
what the post-update check reads.

## Where the verified assets come from

Only the Toolbox's own GitHub Release, over HTTPS, found by the check that exists today (`raul-core::update`). A
release holds the installers and portable archives, `SHA256SUMS` (written by `release.yml` over every asset) and,
new with this ADR, `SHA256SUMS.sig`. The assets an update installs from are the ones that already exist, so no
new packaging is needed for Linux and Windows:

| Install | Asset the update takes | Notes |
| --- | --- | --- |
| AppImage | `raul-<v>-linux-x64.AppImage` | one file; the unit is that file |
| tarball (`.tar.gz`) | `raul-<v>-linux-x64.tar.gz` | the unit is the extracted folder's files |
| portable zip | `raul-<v>-windows-x64-portable.zip` | as above |
| NSIS `-setup.exe` (per user) | `raul-<v>-windows-x64-portable.zip` | the same files the installer lays down, see below |
| deb | none | `raul` does not update a package the system owns |
| dmg | none in this ADR | see "Out of scope" |
| Nix | none | updates through Nix |

Which install this is, is decided from where the running `raul` is: `$APPIMAGE` set means AppImage; a path under
`/nix/store` means Nix; `/usr/bin` or any folder the person cannot write means "not updatable here" (the page then
says so in plain words and keeps the link to the release page); a folder next to `components/` and
`INSTALLED-FILES.sha256` is a tarball, portable or NSIS install. Detection is a pure function of the executable path,
the environment and the files beside it, so it is tested with synthetic folders.

### Verification

1. Download `SHA256SUMS` and `SHA256SUMS.sig` first, each limited to 1 MiB.
2. Check the signature: an ed25519 detached signature over the exact bytes of `SHA256SUMS`, against the public key
   compiled into `raul`. A bad or missing signature stops the update with a plain message; there is no "install
   anyway".
3. Download the asset (limit: 500 MiB, HTTPS only, no redirect off `github.com`/`githubusercontent.com` hosts), hash
   it while writing, and compare with its line in the signed `SHA256SUMS`.
4. Only then open it. Extraction refuses absolute paths, `..`, links that leave the folder and any file not listed in
   the archive's `INSTALLED-FILES.sha256`; every extracted file is hashed against that list.
5. The new version must be higher than the running one (semver); an update never downgrades. Rollback is the only way
   back.

The signing key is a repository secret that the owner creates; the public key is added to `raul` in the pull request
that wires the workflow. Until the secret exists the release is built without a signature and `raul` offers no
install (the release page link stays). This is a decision for the owner to confirm: see the alternatives.

## Replacing the unit atomically and keeping the previous one

The new unit is first fully staged next to the install, on the same filesystem (so a rename can never copy): `raul.new`
and `components.new/` for a folder install, `<name>.AppImage.new` for an AppImage. Nothing of the running install is
touched while staging, so a failed download, a full disk or a bad checksum leaves it as it was.

The swap is a list of renames recorded in a journal first (`update-journal.json` in the Toolbox's data folder, written
and flushed before the first rename), then run in this order for each file of the unit: move the installed file to
`<name>.previous`, move `<name>.new` to `<name>`. A rename is atomic per file; the set is made atomic by the journal:
on every start `raul` reads it and finishes the swap or undoes it, so a crash, a power cut or a kill at any point ends
in either all old or all new. This works on Windows too, where a running `raul.exe` cannot be overwritten or deleted
but can be renamed.

`.previous` files are the previous version, kept for rollback. Exactly one is kept: the next successful update
deletes it after its own check passes; Windows files that are still in use are deleted at the next start. The AppImage's
previous version is `<name>.AppImage.previous`.

## Failure and rollback

- **At install**: the new `raul` is started once as a child process of the running one, with `raul update
  self-check` (a second `raul` is the only process an update starts; no engine or other program). The check reports
  the version it is, reads `INSTALLED-FILES.sha256` and hashes every file against it, checks that the engine build
  is where the unit says it is, and opens the configuration. It has a 60-second limit. If it fails or times out, the
  running `raul` rolls back at once: the journal is reversed, the person sees "The update did not work, so raul went
  back to the old version", with the reason in the copyable details.
- **At the first start after the restart**: the journal still says `swapped`, not `confirmed`, so the new `raul`
  runs the same check on itself and writes `confirmed`. A start that never reaches that point (crash on start) is
  counted; at the second unconfirmed start the next start rolls back by itself, before opening a window.
- **By the person**: while a `.previous` exists, the About and updates page offers "Go back to the previous
  version". That is the same journal reversed, and it keeps the replaced version as the new `.previous`, so going back
  can itself be undone once.
- What a rollback does not touch: settings, Instances, mods, the Rolling-channel engine builds (ADR-0011, in the
  data folder), saves. They are not part of the unit.

## Behaviour per installer

- **AppImage**: stage the new AppImage beside the old one (same folder), verify, rename old to `.previous`, rename new
  into place, check, restart by starting the new file. The running file is a mounted squashfs, so only the file
  itself is renamed, never its contents.
- **deb**: not updated by `raul`. Writing `/usr` needs administrator rights and the package manager's bookkeeping;
  `raul` would break both. The page says a new version exists and links the release page.
- **tarball and portable zip**: the unit is the extracted folder. Same staging and journal.
- **NSIS installer**: a per-user install is a folder like the portable zip's, so the update lays down the portable
  zip's files with the same swap. The installer program is not run again. The Windows "Apps" list therefore keeps
  showing the version it was installed with until the next full reinstall; the uninstaller still removes everything
  because it removes the folder.
- **dmg**: see "Out of scope".
- **Nix**: the page says `raul` was installed with Nix and updates there. No check result is offered as an install.

## Opt-in network use

Nothing is fetched until the person presses the button on the About and updates page. The three steps are three
presses: **Check** (the release list, as today), **Download** (signature file, sums, asset, staging, verification),
**Install** (swap and check), then **Restart**. The check at start stays off unless turned on (ADR-0005) and only ever
runs the check, never a download. No request carries an identifier, as before. Downloads reuse the existing fetch seam
(`curl` through the Runner) behind a `Fetch` trait, so tests use a fake and no test touches the network; an in-process
HTTP client replaces `curl` in a later change and is not needed for this design.

## The code

A `raul-core::selfupdate` module with a trait per outside thing so the core is tested with synthetic fixtures only:
`Fetch` (bytes to a file), `Install` (the detected layout), `Clock`/`Filesystem` use real folders in a temp dir. The
parts: `sums` (parse and verify `SHA256SUMS`, signature), `inventory`, `layout` (which install is this), `stage`
(archive to staging, hashing), `swap` (journal, apply, recover, rollback), `selfcheck`. The CLI is `raul update
download`, `raul update install` (swap, check, rollback on failure), `raul update rollback`, `raul update status`
and `raul update self-check` (used by the swap, not shown in the GUI), all with `--json`; the GUI runs the same jobs
and shows plain words. Delivered in separate pull requests: the verification and inventory, then the swap with
rollback, then the CLI and the release workflow (inventory file, signature), then the GUI buttons.

## Out of scope

- **macOS**: updates through the page link only. The app is a bundle inside a dmg; opening a dmg
  needs `hdiutil` (a process) and a bundle swap interacts with Gatekeeper and translocation. Notarisation is not
  decided here. A `.app.tar.gz` asset and a bundle swap are a follow-up if the owner wants it.
- **Nix packages** update through Nix; **deb** through the package manager.
- Silent background installs, delta updates, release channels, pre-releases and choosing an older version.
- Updating the Rolling-channel engine builds (ADR-0011) and anything under #260/#353.

## Decisions the owner may overrule

1. Verify with an ed25519 signature over `SHA256SUMS`, key embedded in `raul`. Alternatives: only the checksum
   (protects against corruption but not against a compromised release or account); the Sigstore attestation the
   release already has, checked in process (about a hundred more crates, needs the transparency log online) or with
   `gh attestation verify` (needs `gh` and a process). The owner decides whether to create the signing key.
2. Replace file by file with a journal, instead of renaming a whole folder (not possible for a running `raul.exe`
   on Windows) or the platform's `RENAME_EXCHANGE` (Linux only).
3. Keep one previous version next to the install, not in a separate folder: same filesystem, so renames never copy.
   Alternative: a store of versions with a pointer (ADR-0011's shape); rejected for a fixed installer layout.
4. A second `raul` runs the check before the old one exits, then again on first start. Alternative: only the second.
5. NSIS updates from the portable zip's files and does not rerun the installer: a silent installer needs
   `timeout` handling in CI because it hung there, and it would own the rollback. Cost: a stale version in the Apps list.
6. deb and Nix are not updated by `raul`; macOS waits.
7. The unit gains `INSTALLED-FILES.sha256`, generated in `release.yml`.
8. `raul update install` is one command that swaps and checks; `download` is separate so the GUI can show two buttons.

## Consequences

- The release workflow gains two steps (the inventory file and the signature) and a secret.
- A failed update never leaves a half-updated install, and the previous version is one action away.
- Until the play mode lands, an update moves `raul` and the engine build; the engine build then leaves the unit.
- A signed release needs the owner's key; an unsigned release cannot be installed from `raul`.
