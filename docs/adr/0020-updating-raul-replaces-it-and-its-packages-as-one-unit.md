# Updating raul replaces it and its packages as one unit, and rolls back

`raul` can look for a newer release (ADR-0005) but cannot install one: the About and updates page links to the
release page. This ADR decides how `raul` installs a newer release itself (#179). One `raul` version carries one set of
Component versions (ADR-0016), so an update never moves one Component: it replaces `raul` and everything that ships
with it, together, or it changes nothing. No download or install runs until the person asks for it.

## The unit

The **install unit** is every file the release put on the machine for this install: the `raul` program, the
packaged nv-rs engine build under `components/nv-rs/` on Linux and Windows (macOS has none), `THIRD-PARTY-NOTICES.md`
and `LICENSE`. The linked Components (nvmod, loot-rs, lodwright-rs, ttwright-rs) are inside the `raul` file and need no
file of their own. The engine build is the only package that is a separate file, and it stays one until the play mode
(#260, nv-rs#353) links it; then the unit is `raul` plus notices and this ADR needs no change.

Each release adds `INSTALLED-FILES.sha256` to the unit: one `sha256sum` line for every other file in it, generated by
`release.yml` from the staged bundle. It lists every file except itself; its own integrity is that of the archive it
came in, which is checked against `SHA256SUMS` (see Verification). The installed copy of it is what the post-update
check reads.

## Where the assets come from

Only the Toolbox's own GitHub Release, over HTTPS. A release holds the installers and portable archives and
`SHA256SUMS` (written by `release.yml` over every asset). Linux and Windows need no new asset:

| Install | Asset the update takes | Notes |
| --- | --- | --- |
| AppImage | `raul-<v>-linux-x64.AppImage` | one file; the unit is that file |
| tarball (`.tar.gz`) | `raul-<v>-linux-x64.tar.gz` | the unit is the extracted folder's files |
| portable zip | `raul-<v>-windows-x64-portable.zip` | as above |
| NSIS `-setup.exe` (per user) | none in the first version | see Behaviour per installer |
| deb | none | `raul` does not update a package the system owns |
| dmg | none in this ADR | see Out of scope |
| Nix | none | updates through Nix |

Which install this is, is decided from where the running `raul` is: `$APPIMAGE` set means AppImage; a path under
`/nix/store` means Nix; `/usr/bin` or any folder the person cannot write means "not updatable here" (the page then
says so in plain words and keeps the link to the release page); a folder next to `components/` and
`INSTALLED-FILES.sha256` is a tarball, portable or NSIS install. Detection is a pure function of the executable path,
the environment and the files beside it, so it is tested with synthetic folders.

## Verification

Releases are not signed and will not be for a long time (see Future work), so an unsigned release must be installable.
What the checks give, said plainly: they catch a damaged or truncated download and a mix-up of files; they do not
protect against someone who controls the release, because the sums come from the same place as the files.

1. **Pin the release.** The update takes the release for one tag (`v<version>`, the version the check found),
   resolved once through the release's own page, and refuses a draft, a pre-release or a tag whose name does not
   equal the version it offers. The release id is kept for the whole run; every download is built from that
   release's asset list, never from a "latest" address.
2. **Sums first.** Download `SHA256SUMS` (at most 1 MiB), then the asset (at most 500 MiB; HTTPS only; no
   redirect to a host other than GitHub's), hashing as it is written. Compare with the asset's line in `SHA256SUMS`.
   Download `SHA256SUMS` once more afterwards and refuse the update if its bytes changed between the two fetches.
3. **Per-file checks.** Extraction refuses absolute paths, `..`, links and any file not listed in the archive's
   `INSTALLED-FILES.sha256`; every extracted file is hashed against that list, and the copy that is staged is the
   copy that was hashed.
4. **No downgrade.** The version must be higher than the running one (semver); an update to an older or equal
   version is refused unless the person asks for it by name (`--allow-older` on the command line; the page has no such
   button). Rollback is the other way back.

## Replacing the unit atomically and keeping the previous one

The new unit is first fully staged inside the install folder, on the same filesystem (so a rename never copies), under
`.raul-update/new/`. Nothing of the running install is touched while staging, so a failed download, a full disk or a bad
checksum leaves it as it was.

The swap is a list of renames recorded in a journal first (`.raul-update/journal.json`, flushed before the first
rename; the folder entries are flushed after each), then, for each file of the unit: move the installed file to
`.raul-update/previous/<path>`, move the staged file into place. A rename is atomic per file; the set is made atomic by
the journal: `raul` reads it on start and finishes by undoing an interrupted swap, so a crash, a power cut or a kill at
any point ends in all old. A lock file in `.raul-update/` keeps two processes (the page, the command line, a start-up
recovery) from changing the install at once. Files must be plain files: links and folders in the unit are refused. This
works on Windows too, where a running `raul.exe` cannot be overwritten or deleted but can be renamed (to be confirmed
by the three-OS CI; see option (c) below for the fallback).

Exactly one previous version is kept. The next update sets it aside (not deleted) while it swaps, and deletes it only
after that swap finished, so an interrupted update never loses the rollback target. On Windows a file that is still in
use cannot be deleted; it is retried at the next start and never blocks an update.

## Failure and rollback

- **At install**: the new `raul` is started once as a child process of the running one, with `raul update self-check`
  (a second `raul` is the only process an update starts). The check reports the version it is, reads
  `INSTALLED-FILES.sha256` and hashes every file against it, checks that the engine build is where the unit says it is,
  and opens the configuration. It has a 60-second limit. If it fails, times out **or never starts** (no such file, not
  executable, killed at once), the running `raul` rolls back immediately and says so; this is the case that protects
  against a new binary that cannot run at all, and it is why the check runs before the old process exits.
- **At the first start after the restart**: the journal says `swapped`, not `confirmed`, so the new `raul` runs the same
  check on itself and confirms. A start that never reaches that point (crash on start) is counted; the next start
  finds the count and rolls back by itself, before opening a window. If the new `raul` cannot run at all
  and the old one has already exited, nothing can run the recovery: the previous version sits in
  `.raul-update/previous/` (an AppImage's in `<name>.AppImage.previous`) and the release notes say how to put it back by
  hand or to install again. This is the accepted residue of replacing a program with itself.
- **By the person**: while a previous version exists, the page offers "Go back to the previous version": the same
  journal reversed. The replaced version stays in the staging folder until the next update replaces it.
- **What a rollback does not touch**: settings, Instances, mods, the Rolling-channel engine builds (ADR-0011) and
  saves. In particular the engine copy inside an Instance (`nv-rs/` in the Instance, put there by the Engine step) is not
  part of the unit: an update does not change it, and a rollback does not revert it. After an update or a rollback the
  packaged engine and the Instance's copy can therefore differ; Home already says "the engine differs from its install
  record", and the Engine step puts the packaged one in again when the person asks. Following the packaged engine
  automatically is a follow-up, not part of this ADR.

## Behaviour per installer

- **AppImage**: stage the new AppImage beside the old one (same folder), verify, rename old to `.previous`, rename new
  into place, check, restart by starting the new file. Only the file itself is renamed (the running one is a mounted image).
- **deb**: not updated by `raul`; writing `/usr` needs administrator rights and the package manager's bookkeeping. The
  page says a new version exists and links the release page.
- **tarball and portable zip**: the unit is the extracted folder. Same staging and journal.
- **NSIS installer**: not updated by the file swap in the first version. A per-user install is a folder like the
  portable zip's, but the installer also owns shortcuts, the uninstall entry and its file list; a swap would leave
  the Apps list showing the old version and the uninstaller unaware of files a newer version adds. Until a helper can
  run the new installer (option (c)), an NSIS install shows the new version and the link to the release page.
- **dmg**: see "Out of scope". **Nix**: the page says `raul` was installed with Nix and updates there.

## Opt-in network use

Nothing is downloaded or installed until the person presses a button (or runs the command). The steps are separate
presses: **Check** (the release list, as today), **Download** (sums, asset, staging, verification), **Install** (swap
and check), then **Restart**. The check at start from ADR-0005 stays off unless turned on and only ever reads the
release list; it never downloads. No request carries an identifier. Downloads reuse the existing fetch seam (`curl`
through the Runner) behind a `Fetch` trait, so tests use a fake and no test touches the network.

## Options for self-updating and updating from the command line

| Option | Fits | Needs from CI | Unattended | Verdict |
| --- | --- | --- | --- | --- |
| **(a)** `raul` downloads the platform archive and swaps files (this design) | AppImage, tarball, portable zip, Windows portable | `SHA256SUMS`, `INSTALLED-FILES.sha256` in the archives | no: starts only on a press or command | **Build first** |
| **(b)** re-run the platform installer or package (NSIS `/S`, `dpkg -i`, AppImageUpdate, mounting a dmg) | NSIS, deb, dmg, AppImage | installer assets (exist); zsync files for AppImageUpdate | NSIS silent install hung in CI before; deb needs root | Later, for NSIS only, through (c) |
| **(c)** a tiny separate helper that swaps after `raul` exits | Windows (running-exe locks), NSIS (runs the installer after exit) | one more small binary in the unit, built by CI | runs only after a press | **Only if the Windows CI shows renaming the running exe is not enough, or for NSIS** |
| **(d)** package managers: Nix flake update, apt repository, winget, scoop, brew taps | Nix, deb, Windows, macOS | hosting for an apt repository (which needs signing, shelved); manifests for winget/scoop/brew that point at the release assets with their sums | by the package manager's own schedule, outside `raul` | Not `raul`'s job; add manifests when someone asks. Nix needs nothing |
| **(e)** a crate (`self_update`, `self-replace`) instead of a hand-written swap | single-file installs | none | n/a | Rejected: they replace one executable, our unit is several files and needs a journal and rollback; `self_update` also brings its own downloader and signature scheme |
| **(f)** delta or zsync downloads | AppImage | zsync metadata per release | n/a | Later; the archives are small enough for the first version |
| **(g)** a pure command-line flow `raul update check`, `download`, `install`, `rollback`, `status`, usable headless and over SSH, that the page calls | every updatable install | nothing beyond (a) | no | **Build first, with (a)**: the page is a thin caller of the same commands' code |

Recommendation: build (a) behind (g) first, for the AppImage, tarball and portable-zip installs; keep (c) as the
planned fix if renaming a running `raul.exe` does not hold on Windows CI and for NSIS; leave (d) to the package
managers. Linux needs no helper. The portable swap core (`raul-core::selfupdate::swap`, #325) is the same under every
option, so choosing (c) later changes only who calls it.

## The code

A `raul-core::selfupdate` module with a trait per outside thing so the core is tested with synthetic fixtures only:
`Fetch` (bytes to a file), and real folders in a temp dir for the rest. The parts: `sums` (parse and verify
`SHA256SUMS` and the per-file list), `layout` (which install is this), `stage` (archive to staging, hashing), `swap`
(journal, lock, apply, recover, rollback; #325), `selfcheck`. The CLI is `raul update check|download|install|rollback|status`
and `self-check` (used by the swap), all with `--json`; the GUI runs the same code and shows plain words. Delivered in
separate pull requests: the swap, then verification and staging, then the CLI and the release workflow (the inventory
file), then the GUI buttons.

## Out of scope

- **macOS**: updates through the page link only. Opening a dmg needs `hdiutil` (a process) and a bundle swap interacts
  with Gatekeeper. Notarisation is not decided here.
- **Nix packages** update through Nix; **deb** through the package manager.
- Silent background installs, release channels, pre-releases and choosing an older version except by `--allow-older`.
- Updating the Rolling-channel engine builds (ADR-0011) and anything under #260/#353.

## Future work: signatures

Releases are not signed and no signed release is required. A signature scheme (a detached signature over `SHA256SUMS`,
a key kept outside the repository, rotation and revocation) is a possible later step; this design leaves a place for
it (the verification of the sums) and installs without it. Nothing here needs a secret or a key.

## Decisions the owner may overrule

1. Verification is the sums from the same release over HTTPS, pinned to the release tag, with a second fetch of the sums
   to catch a change, plus per-file checks. Alternatives: signatures (shelved), Sigstore attestations (a hundred more
   crates, or `gh` and a process).
2. Replace file by file with a journal and a lock (confirmed), not a whole-folder rename (not possible for a running
   `raul.exe`) or `RENAME_EXCHANGE` (Linux only).
3. Keep one previous version inside the install folder (same filesystem, so renames never copy).
4. A second `raul` runs the check before the old one exits, then again on first start; a check that cannot start
   counts as a failure.
5. NSIS, deb, dmg and Nix are not swapped by `raul` in the first version.
6. The unit gains `INSTALLED-FILES.sha256`, generated in `release.yml`.
7. An older version is refused unless `--allow-older` is given.
8. The Instance's engine copy is outside the unit; a mismatch with the packaged engine is shown, not fixed.
9. Build (a) behind (g) first; (c) only when needed.

## Consequences

- The release workflow gains one step (the inventory file). No secret.
- A failed update never leaves a half-updated install while the old `raul` is alive, and the previous version is one
  action away.
- Until the play mode lands, an update moves `raul` and the engine build; the engine build then leaves the unit.
